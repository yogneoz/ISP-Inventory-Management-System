# Fresh-eyes audit and corrections — 2026-11-28

A full-stack reliability review of the running system (React + TypeScript client,
Node/Express server, PostgreSQL) with the corrections applied in the same
working tree. It supersedes `audit-2026-11-15.md` as the current reliability
audit; that document stays as dated evidence for the payload and hydration work.

Scope of the review: transaction boundaries and lock coverage, schema
constraints, N+1 and index usage, migration safety, in-memory state versus the
database, SSE invalidation, API contract drift, idempotency, RBAC consistency
and audit trails.

Verdict: **the transactional core is sound and the ledgers are correct**; the
defects were all at the *edges* of a transaction — what the system told other
people while a write was still open, and which copy of the truth a read used
when the database was slow. Three were serious enough to corrupt what a user or
an auditor sees.

## The critical findings, in detail

### C1 — a write told the world it had happened before it had

**Where.** `server/src/services/audit.service.ts` (the two `broadcastChange`
calls and the `setAuditTrail` prepend), reached from every controller that calls
`logAuditEvent(req, …, client)` inside `withTransaction`
(e.g. `server/src/controllers/sales.controller.ts`, `postSalesInvoiceLedger`
path).

**The flaw.** `logAuditEvent` built its row, prepended it to the in-process
audit mirror and pushed two SSE events immediately — while the INSERT it was
recording had not committed. The client reacts to an event by re-fetching the
affected slice, so the refresh read a database where the row did not exist yet
and the new document vanished from the screen until the next unrelated reload.
Worse, a transaction that then failed (insufficient stock, closed period, a
deadlock victim) had already announced a change that never happened and left a
phantom row in the mirror.

**The fix.** A new `server/src/db/afterCommit.ts` provides a request-scoped
`AsyncLocalStorage` queue. `withTransaction` opens one scope per attempt, runs
the queue after `COMMIT`, and discards it on any error (`ROLLBACK` included); a
retry therefore starts empty instead of replaying the aborted attempt's
broadcasts. `logAuditEvent` registers its mirror prepend and both broadcasts
through it. Outside a transaction (demo mode, CLI, `logAuditEvent` without a
`client`) the callback runs immediately, so no other caller changes behaviour.
`AsyncLocalStorage` rather than a module variable because concurrent requests
interleave at every `await`.

### C2 — RBAC was enforced from a per-worker copy

**Where.** `server/src/state/runtimeState.ts` (`setPermissionMatrix`,
`setUserPermissionOverrides`, `setUserPermissionSetGrants`),
`server/src/middleware/index.ts:357` (`effectivePermission(...)` reading those
bindings), `server/src/state/cacheInvalidation.ts`.

**The flaw.** The reference caches already fan out a write to every worker
(A3), but the permission caches did not — they were not `CACHE_LOADS` entries
and their setters never announced. `permissions.controller.ts` published the
committed matrix/override to the *serving* worker's memory only. Under
`instances: 'max'` the next request that landed on another worker was authorized
against the old matrix: a revoked grant stayed usable and a newly granted one
kept answering 403, decided by the load balancer.

**The fix.** The three setters announce through the existing cache hook under a
reserved name (`PERMISSIONS_CACHE_NAME = 'permissions'`,
`server/src/state/cacheWriteHook.ts`). `cacheInvalidation.ts` accepts that name,
re-reads the matrix, the overrides and the set grants **together** and publishes
them to the enforcement path, and bumps the client-facing version. An
`applyingRemote` flag suppresses the announcement during a remote apply, so two
workers cannot echo invalidations forever.

**The proof.** `scripts/verify_permission_fanout.ts`
(`npm run verify:permissions-fanout`) is the cross-process half the
single-process suite could not show, and Redis being a deployment requirement
now is what gives it a real server to run against: `redis:7-alpine` in CI,
`redis-server` 7.0.15 on the development host. What it asserts, and the one
mutation it was checked against, are recorded under "What a test now proves"
below.

### C3 — a closed fiscal year could still receive journals

**Where.** `server/src/models/accounting.repo.ts` (`FISCAL_YEAR_BOUNDS_SQL`),
`server/src/services/accounting.service.ts` (`fiscalYearForDate` →
`ensureOpenPeriod` → `postJournal`), against
`server/src/models/admin.repo.ts` (`FY_CLOSE_SQL`).

**The flaw.** A posting resolved its fiscal year with a plain `SELECT`, then
inserted a journal and its period balances. The close is an `UPDATE …
is_closed = TRUE`, which locks the row — but the posting held no lock on it, so
the close could commit between the posting's read and its inserts. The closed
year then carried journals that no closing snapshot accounted for, and because
the ledger is append-only, the year's figures stayed wrong. The HTTP-level
fiscal gate does not close this: it reads the boot-time `fiscalYears` cache.

**The fix.** `FISCAL_YEAR_BOUNDS_SQL` ends in `FOR SHARE`. A posting that reads
first now makes the close wait, so the close's snapshot includes that journal (it
was posted before the close). A close that commits first makes the posting's
locking read wait and then return `is_closed = true`. It is a shared lock, so
concurrent postings into the same year never block each other.

**The second half — a posting that starts after the close.** Lock ordering only
orders two transactions that overlap; it does not make the *next* posting read
the flag. `postJournal` → `ensureOpenPeriod` now refuses a journal date inside a
closed fiscal year with a `409` naming the year. The check lives in the service,
not in the route, because the fiscal-year HTTP gate is not the only way into the
ledger: an outbox flush and service-to-service callers reach `postJournal`
without ever passing through Express. The one documented exception survives — a
Super Admin override with a written reason, which
`enforceFiscalYearWriteAccess` already audit-logs — carried per request by
`server/src/state/fiscalWriteOverride.ts` (`AsyncLocalStorage`, the same
request-scoped shape `server/src/db/afterCommit.ts` uses), so the override still
posts and nothing else does.

**The proof.** `tests/fiscalCloseRace.concurrency.test.ts` drives the real close
(`closeFiscalYear`) against the real posting (`postJournal`) on genuine pool
connections, in a throwaway database it owns — a closed year is company-wide and
single-shot, so the shared database cannot host it. Three connections take part:
one posting, one closing, and one that parks the posting *inside* `postJournal`
(after the fiscal year is resolved, before the journal is written) by holding the
document-sequence row the posting claims next. In that window the close must
wait, and its own `lock_timeout` proves that it did (SQLSTATE `55P03`) instead of
hanging the suite; the year must still be open; the posting then commits into the
still-open year; and the close, retried, lands with that posting in its snapshot.
A second test proves the other order — after the close commits, the same posting
is refused `409` and writes nothing — and a third proves the audited override
still posts.

The refusal also exposed a latent bug on the same path, which is repaired here:
`postOpeningBalances` posted an opening journal on the *period's* calendar start
date. A Nepali fiscal year begins mid-month, so the first period of 2082-83
(2025-07) starts on 2025-07-01, which by date falls inside 2081-82 — a different,
already closed year. Opening balances therefore resolved to the closed year.
`EARLIEST_OPEN_PERIOD_SQL` now returns its year's start alongside the period, and
the opening posts on the later of the two, so a boundary period stays inside the
year it belongs to. This is also what turned `AUTHZ-12`/`AUTHZ-13` red before the
repair: those registers were posting into the closed 2081-82 in the development
database.

Why the parking window is the whole design: a posting that has already inserted
its journal needs no help from `FOR SHARE`, because `gl_journals.fiscal_year_id`
carries a foreign key to `fiscal_years` and that FK check takes a `KEY SHARE` row
lock of its own. A test that posted first and closed second would therefore stay
green with `FOR SHARE` deleted. That was measured during the work, not assumed,
before the parked-posting version was written.

## The high findings, in detail

**H1 — a slice endpoint that would have answered `[]` for the audit trail.**
`server/src/controllers/bootstrap.controller.ts` kept a last-resort
`cacheSlices` map that included `auditLogs: auditTrail`. That binding is not
hydrated on a PG-connected server (OPS-3 took the audit trail off the boot
fan-out), so the key would have answered an empty array — which the client
stores as "the audit trail is empty" — instead of the honest 503 the same key
already returns when its live read fails. The entry is removed. The `assets:
assetRegister` entry beside it deliberately stays: `tests/fixedAssetsOffBootstrap.test.ts`
pins it as the compatibility answer an older client bundle still receives, and
the live slice read always runs first.

**H2 — a stale stock read dressed as a fresh one.**
`server/src/controllers/inventory.controller.ts` `get_stock` fell through to the
in-memory `inventoryStock` projection when the live query threw. That projection
is hydrated once at boot and never re-read, so a transient database error
answered 200 with yesterday's quantities — and the sale, dispatch and partner
gates downstream decide on those numbers. On a PG-connected server it now
answers `503 DB_UNAVAILABLE`; the mirror is served only in demo mode, where it
*is* the register.

**H3 — one millisecond, two events, one refresh.**
`server/src/realtime/sse.ts` set `dataVersion = Date.now()` per broadcast, while
`client/src/hooks/useSyncStream.ts` only refreshes when
`event.dataVersion > serverDataVersionRef.current`. Two events in the same
millisecond therefore carried the same number and the second was dropped — the
class of "I saved it twice and the screen shows one" bug that is impossible to
reproduce on purpose. `advanceDataVersion()` returns
`Math.max(now, previous + 1)`, which stays on the wall-clock scale the bootstrap
version uses while guaranteeing a distinct number per event.

**H4 — the table had no floor.**
Every write path guards itself (`WHERE quantity_on_hand >= qty`), but nothing
guarded the table: a manual `UPDATE`, a restore or a future writer could leave a
negative balance and every total downstream is then wrong. `scripts/schema.sql`
and the new `scripts/migrations/0063_inventory_stock_nonnegative.sql` add
`inventory_stock_qoh_nonnegative`. Both use `NOT VALID` + a guarded `VALIDATE`,
so an installation that already holds a bad row upgrades instead of failing —
the constraint still enforces every INSERT and UPDATE from the moment it exists —
and a healthy install (and every fresh one) ends up validated, identical on both
paths.

**H5 — one round trip per invoice line.**
`server/src/controllers/sales.controller.ts` ran `SI_DEDUCT_STOCK_SQL` once per
line inside the invoice transaction. `SI_DEDUCT_STOCK_BATCH_SQL`
(`server/src/models/sales.repo.ts`) sums the wanted quantity per product and
deducts the whole invoice in one statement. The all-or-nothing rule is
unchanged: a product that cannot cover its total matches no row, the caller
compares the returned row count with the number of distinct products and aborts,
and the rows that did update roll back with the transaction. Each movement row
still records its own true before/after pair, recovered by walking the lines and
adding back what has not left yet.

**Measured, not asserted (2026-11-28).** `tests/salesStockDeductionBatch.test.ts`
settles the claim twice over, against the development PostgreSQL:

- *Structure.* It patches `pg.Client.prototype.query` to count every statement
  that updates `inventory_stock`, then posts a real 40-line sales invoice through
  `POST /api/sales-invoices` on the real Express app. Exactly **one** such
  statement is issued. Restoring the per-line loop in the controller turns the
  test red — `actual: 40, expected: 1` — and restoring the batched statement turns
  it green; that mutation was run, not assumed. Every product's balance still
  moves by its own sold quantity, so "one statement" is not "some lines skipped".
- *Cost.* The same deduction run both ways on that database, inside a transaction
  that is rolled back, alternating the order and repeating nine times, medians:
  **batch 1.7–2.9 ms / 1 statement vs per-line 23–43 ms / 40 statements** — 21 to
  40 ms saved per 40-line invoice, roughly 0.5–1.0 ms per avoided round trip.
  Those ranges are the four intact runs: two standalone (2.11 vs 23.17 ms, 2.48
  vs 27.28 ms) and two full-suite runs (2.90 vs 43.10 ms, 1.73 vs 30.02 ms), which
  saved 21.06, 24.80, 40.20 and 28.30 ms. The spread is the machine (shared,
  other work running), not the mechanism. The conservative end is the honest
  headline: **at least ~20 ms per 40-line invoice**, and the saving scales with
  the line count because it is one round trip per line that disappears.

Conditions: development workstation, loopback to the local PostgreSQL, 40
distinct products x 1 unit on one branch, one pooled connection, warm cache,
`statement_timeout` 20 s, nine alternating repetitions, median per repetition;
the measured work is rolled back and the fixture's balances are asserted
unchanged afterwards. What this does **not** measure is contention: the per-line
path also held each stock row lock for its own round trip, which this harness
cannot see because it runs one invoice at a time. The absolute saving is small
next to a journal posting; the finding was about round trips scaling with line
count, and that is what is now measured.

**H6 — audit rows that silently overwrote each other.**
`logAuditEvent` minted `aud-${Date.now()}-${100..999}`. Two rows in the same
millisecond could collide, and the INSERT's `ON CONFLICT DO NOTHING` then
dropped one without a trace — in an audit trail, of all places. The id is now
`aud-${randomUUID()}`.

## Accepted, deferred and verified

**M1 — `if (rows.length > 0)` in `CACHE_LOADS` (accepted).** An empty table
leaves the previous binding in place. That is deliberate for the seeded
reference tables (a failed or half-finished restore must not blank the branch or
user list), and the two tables where an empty result is meaningful —
`inventory_stock` and `products` — apply unconditionally. Recorded here so the
guard is not "fixed" into an outage by a later reader.

**M2 — partner consumption idempotency (deferred).** The pre-check in
`server/src/services/integration.service.ts` runs before the write transaction.
The database itself is the real guard: `stock_consumption_events` carries
`UNIQUE (partner_id, external_id)`, so a replay cannot apply twice; what the
pre-check buys is a clean `409` instead of a constraint error. Moving it inside
the transaction would trade a friendly message for no additional safety, so it
stays, with the unique key as the invariant.

**M3 — `permissionsVersion` (partly fixed).** The counter is still per worker;
what changed is that every worker now re-reads the committed state and bumps
its own counter, so a client that reads the version from two workers can still
see two numbers. The number is advisory (the client re-reads permissions on
login and on the `PERMISSIONS` SSE event), so this is recorded rather than
enlarged.

**M4 / M5 — mirror reads in `patch_Id` and `globalSearch` (verified, not
defects).** Both are inside `if (!getPgConnected())` blocks: they are the demo
mode register, not a fallback for a failed query.

**L1 — duplicate index (verified, deliberate).** `idx_stock_prod_branch` is a
legacy alias kept as a no-op so upgraded deployments that only ever ran `dbBoot`
keep their coverage; `scripts/schema.sql` documents it in the alias block.

## Why the schema change needed no other edit

The new CHECK lives in `scripts/schema.sql` **and** in a numbered migration, and
both run the same two idempotent `DO` blocks, so `verify:fresh-install` compares
two schemas that converge on one constraint with the same name and the same
validated state. The migration is idempotent (guarded on `pg_constraint`), so a
database that already booted from `schema.sql` replays it as a no-op.

### What a test now proves, and what it does not

- **C3 — proven, both interleavings.** `tests/fiscalCloseRace.concurrency.test.ts`:
  *"a posting parked before its journal write holds the close back, and the close
  lands once it commits"* and *"a posting after the close observes is_closed and
  is refused"*, plus *"the audit-logged Super Admin override still posts into the
  closed year"*. It was checked against the code it pins: deleting `FOR SHARE`
  from `FISCAL_YEAR_BOUNDS_SQL` turns it red on *"the close must be blocked by the
  in-flight posting itself"*, and restoring the clause turns it green again.
  Deleting `FOR UPDATE` from `FISCAL_YEAR_CLOSE_LOCK_SQL` does **not** turn it
  red — the closing `UPDATE` needs the same row, so the close still waits. The
  close is guarded twice, and the test records that by staying green.
- **C2 — proven across two processes, with a negative control.**
  `scripts/verify_permission_fanout.ts` (`npm run verify:permissions-fanout`)
  runs worker B as a **child process** against a real Redis 7 and the real
  PostgreSQL: it subscribes, hydrates its three RBAC caches and evaluates
  `effectivePermission` — the resolver `requirePermission` calls — for a temp
  user on an operation the user's role does not have. Worker A commits a `grant`
  override and tells worker B it is committed; **worker B still denies**, which
  is the negative control and the exact shape of the original defect. Worker A
  then publishes the way `permissions.controller.ts` does after `COMMIT` — read
  the rows back and call `setUserPermissionOverrides`, whose write hook announces
  `permissions` on `isp:cache:invalidated` — and worker B, on the message alone,
  re-reads all three tables and now allows that operation, with
  `permissionsVersion` 2 → 3. Removing the announcement turns it red:
  `published: false`, worker B still denying after 20 s, exit 1. That mutation was
  run, not assumed. `tests/referenceCacheInvalidation.test.ts` keeps pinning the
  declaration side (two independent subscribers on one store), so a refactor that
  drops one of the three announcements still fails the suite; the script is the
  delivery half. Both run on every push: `build-and-boot-timing` owns the
  `redis:7-alpine` service and runs the proof as a step.
- **H5 — measured.** `tests/salesStockDeductionBatch.test.ts` pins one
  stock-deduction statement per invoice (red at 40 statements when the per-line
  loop is restored) and measures both shapes on the development database (numbers
  above). The timing is recorded, not asserted: a wall-clock assertion on a shared
  workstation is a flake generator.

## What this audit did not do

- It did not drive the UI in a browser. Every statement above is about server
  behaviour and schema, verified through the type checker, the guards and the
  test suite.
- It did not measure throughput or lock contention. H5's round-trip claim is now
  measured (numbers above), but no multi-client concurrency benchmark was run, so
  no throughput figure is claimed.
- Concurrency is proven only where a test drives it. C3 has two executed
  interleavings against a real close (above); C2 has two OS processes on a real
  Redis, driven by `npm run verify:permissions-fanout` (above) rather than by a
  `node:test` file, because it needs a second process and a server the unit suite
  does not start.
