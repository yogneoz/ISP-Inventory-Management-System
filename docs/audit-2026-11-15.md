## 1. Executive Summary

### Overall risk rating: **MEDIUM-HIGH — CONDITIONAL GO**

The **application code is in good shape**; the **operational envelope around it is not ready**.

What the audit found, in one paragraph: this is a disciplined, unusually well-tested single-tenant ERP.
Business logic is layered (49 controllers / 58 services / 47 repositories), SQL is confined to
repositories by a build gate, the ledger is append-only at the database level, migrations are
checksum-immutable, and 290 test files / 2,411 tests — including real-PostgreSQL concurrency and
drift guards — pass. No authentication bypass, no privilege-escalation path, no data-corruption
defect and no critical (Remote-Code-Execution / auth-bypass / ledger-tampering) vulnerability was
found. Against that, five things block a responsible go-live:

1. **There is no backup or recovery capability.** A single PostgreSQL instance is the sole source of
   truth; the only backup guidance in the repository is one ad-hoc `pg_dump` line in the README.
   No schedule, no off-host copy, no restore rehearsal, no point-in-time recovery, no RPO/RTO.
   The system also ships an operator command (`npm run setup:pg`) that drops and recreates the
   schema. One disk failure or one mistaken command destroys the company's financial history.
2. **The login/bootstrap path does not scale to the stated user population.** A single endpoint
   (`GET /api/bootstrap`, 155 KB per response, required on every login and refresh) measured
   **2.3 s p50 / 4.2 s p95 at 50 concurrent users**, and in one of two cold runs produced 29/120
   failures plus a multi-second window in which the API reported "PostgreSQL is not connected" to
   every caller. The README's target is 500 users.
3. **Credential handling is weaker than the rest of the security model.** The admin user-create
   endpoint silently assigns the password `password@123` when none is supplied, password reset
   accepts three characters, and created accounts are not forced to change either. There is no
   server-side logout or token revocation list.
4. **Nothing is encrypted at rest, and transport is plain HTTP by design.** Employee salary and
   bank details, customer PII and the whole ledger sit unencrypted on a LAN host; HSTS is
   deliberately disabled and no TLS proxy is configured in this repository.
5. **Error handling leaks internals.** 71 response sites return raw `err.message` (SQL/constraint
   text) to callers, and the unauthenticated `/api/db/status` publishes DB host, port, database
   name, DB user and the raw probe error.

Everything else in this report is Medium or Low, and most of it is polish around an otherwise
sound product: documentation counts that are off by 2×, 121 unindexed foreign-key columns, a
BS-calendar seeding gap that silently drops 25% of days from fiscal-year reports, and the absence
of email/SMS, MFA, OpenAPI and formal requirements.

## 2. Scope, Method and Environment

**Reviewed:** architecture and modularity; API surface; coding practice and technical debt; schema,
constraints, migrations, triggers and partitioning; authentication, authorization, rate limiting,
transport and storage security; module coverage against the README's stated business scope and the
`docs/tasks/*` initiative notes; and measured performance of boot, reads, writes and concurrency.

**Method:** static reading of the security and data paths; live introspection of the running
PostgreSQL 16 database; execution of the project's own gates (`tsc`, guard scripts, fresh-install
parity, bundle/boot budgets); and load measurement against a locally running server. Where a claim
could not be evidenced it is listed as an evidence gap, not as a defect.

**Environment caveat:** all timings were taken on the Windows development workstation
(loopback HTTP, `tsx watch` dev process, demo-seeded database), not on the target server, not behind
TLS, and not through the production build. They are therefore **lower bounds for latency and upper
bounds for throughput** relative to a production host — except where the single-process design
itself is the limiter, in which case they transfer directly.

## 4. Findings Log

Severity key: **Critical** = must fix before go-live, data-loss or outage class.
**High** = must fix before go-live or accept in writing. **Medium** = fix within the first month.
**Low** = backlog.

### Critical

#### C1 — No backup, restore or disaster-recovery capability exists
**Evidence.** A repository-wide search for `pg_dump|pg_basebackup|BACKUP` across `scripts/`,
`server/`, `docs/` and `README.md` returns exactly one hit: `README.md:531`, a suggestion to run
`pg_dump -U inventory_user -h localhost inventory_db > backup_$(date +%Y%m%d).sql`. There is no
backup script among the 28 scripts in `scripts/`, no cron/PM2/systemd timer, no WAL archiving, no
off-host destination, and no document in `docs/` covering restore or disaster recovery. The boot
log states the design explicitly: *"Operational data is always served from PostgreSQL (single
source of truth)"* — in-memory mirrors are not a recovery path. `npm run setup:pg` drops and
recreates the schema, so the most-used operator command is itself a total-loss event.

**Impact.** Disk failure, filesystem corruption, ransomware or a single mistaken command destroys
all financial history with no defined RPO or RTO and no tested way back. This is the only finding
in the report whose worst case is *unrecoverable*.

**Remediation (P0).**
1. Nightly `pg_dump -Fc` to an off-host location plus continuous WAL archiving (pgBackRest or
   WAL-G) for point-in-time recovery; retain 30 daily / 12 monthly, encrypted at rest.
2. `scripts/backup.sh` and `scripts/restore.sh` committed alongside the app, plus a
   `check:restore-drill` script that restores the latest dump into a scratch database and asserts
   row counts, `gl_journals` debit/credit balance and the trial-balance checksum.
3. Weekly automated restore rehearsal with alerting on failure; a written runbook stating
   **RPO ≤ 15 min, RTO ≤ 2 h** and who executes it.
4. Add a confirmation guard to destructive operator commands (`setup:pg` should refuse without an
   explicit `--force` and a verified backup younger than 24 h).

### High

#### H1 — `/api/bootstrap` collapses at 50 concurrent users and can flip the whole API to "database down"
**Evidence.** Measured: at 10 concurrent, p50 241 ms; at 50 concurrent, p50 2,339 ms / p95 4,208 ms,
155 KB per response, ~22 rps. In one of two cold 50-concurrent runs, **29 of 120 requests failed**
and the server log then showed a cascade:

```
PostgreSQL query failed: timeout exceeded when trying to connect
PostgreSQL bootstrap query failed: timeout exceeded when trying to connect
PostgreSQL query failed: Connection terminated due to connection timeout
PostgreSQL bootstrap query failed: PostgreSQL is not connected. Database operations are unavailable.
```

The mechanism is in `server/db.ts:170-190` (`isConnectionLevelFailure`) and `server/db.ts:195-210`.
Pool-acquire timeouts are correctly excluded, but the socket-level message
`Connection terminated due to connection timeout` matches `/Connection terminated/` and sets the
**global** `isPgConnected = false`, after which every `pgPool.query` throws
`PostgreSQL is not connected…` until `ensurePostgresConnection()` re-probes. A short queue therefore
turns into an API-wide outage for every user, not just the saturated caller.

**Impact.** The endpoint is on the login and refresh path, so a shift-start burst is exactly the
worst case. At the stated 500-user target the observed curve (2.3 s p50 at 50) is far outside any
usable envelope.

**Remediation (P0).**
- Make the DB-availability flag require N consecutive connection-level failures and recover on the
  next successful query (circuit breaker); never flip on a connect-path timeout. Distinguish
  acquire/connect `ETIMEDOUT` from a terminated established socket.
- Return `503 Retry-After` per request instead of poisoning the global flag; the pool timeout should
  fail only that request (the code comment already intends this — the classifier does not achieve it).
- Cut the payload: ETag/`If-None-Match` on `/api/bootstrap`, delta refresh through the existing SSE
  channel, and split rarely-used registers out of the payload (155 KB per login is the root cause of
  the queue).
- Raise `PG_POOL_MAX` (default 40) to match measured concurrency, add `statement_timeout` and
  `PG_CONNECT_TIMEOUT_MS` tuning per environment.
- Add a repeatable load gate at the target concurrency to CI or a nightly job.

#### H2 — Weak credential policy on administrative user management
**Evidence.**
- `server/src/controllers/admin.controller.ts:325` — user creation hashes
  `String(req.body.password || 'password@123')`: **if the field is omitted the account is created
  with a publicly known password**, and the response does not indicate it.
- `server/src/controllers/admin.controller.ts:427` — password reset rejects only below **3**
  characters.
- `server/src/controllers/auth.controller.ts:412` — self-service change requires only 8 characters;
  there is no complexity rule, no breached-password check and no reuse prevention.
- `must_change_password` is set only for employee-linked logins (`server/src/models/admin.repo.ts:335-344`),
  not for accounts created or reset through `post_users` / `post_resetPassword`.
- No server-side logout: "logout" exists only client-side (`client/src/services/api/sync.ts:194`),
  so a copied token stays valid for its full 8-hour TTL (`server/src/middleware/auth.ts`).

**Impact.** An administrative action can silently create an account with a guessable password that
the holder is never asked to change, on a system that posts journals. Combined with a login limiter
that allows 10 attempts/minute per IP, that is a realistic path into a finance-capable account.

**Remediation (P0).**
- Remove the default password; require an explicit value on create and set `must_change_password`.
- Minimum 12 characters (or passphrase) on all set/reset paths, block the top-1,000 common
  passwords, and force rotation on reset.
- Add an authenticated `POST /api/auth/logout` plus a server-side token deny-list/`ver` bump so
  sessions can actually be ended; shorten TTL with a refresh path.
- Add TOTP MFA for `SUPER_ADMIN` and `HEAD_OFFICE_ADMIN` (see M4).

#### H3 — No encryption at rest; plaintext HTTP is the default transport
**Evidence.** No `pgcrypto`, column encryption or application-level encryption anywhere in
`server/` or `scripts/schema.sql`; PostgreSQL stores employee salary/bank data, customer PII and the
entire ledger in plaintext. `server/src/app.ts:236-249` disables HSTS and clears
`upgrade-insecure-requests` deliberately because the app serves plain HTTP on the LAN; no TLS
termination (nginx/caddy/stunnel) is configured or documented in this repository. `TRUST_PROXY` is
off by default (a correct fail-safe), which confirms the current topology is direct HTTP.

**Impact.** Anyone with disk, backup-media or LAN access reads all payroll and financial data; there
is no confidentiality control that survives the host. Nepal's Privacy Act 2075 requires reasonable
security safeguards for personal data and breach notification, and the Income Tax Act requires
retention integrity — neither can be evidenced today.

**Remediation (P0/P1).**
- Terminate TLS in front of the app (or `sslmode=verify-full` to PostgreSQL) and re-enable HSTS once
  HTTPS is the only path; set `TRUST_PROXY=1` **only** with the exact hop count.
- Enable full-disk encryption on the server and on backup media.
- Encrypt the highest-sensitivity columns (`payroll`, employee bank/citizenship/PAN, customer contact
  data) with `pgcrypto` or application-level envelope encryption, with keys outside the database.
- Write the data-protection pack: retention schedule, subject-access and erasure procedure, breach
  notification runbook, and a register of personal-data fields.

#### H4 — Write path amplifies work and cannot scale past one process
**Evidence.** `npm run bench:write` reports 11 `CACHE_LOADS` entries re-read after **every** committed
write (branches, users, uom, locations, suppliers, fiscalYears, companyProfile, products, categories,
product_groups, inventory_stock). Ten concurrent writes took **210.8 ms** wall against a 154.0 ms
serial-equivalent — **0.7× scaling, i.e. concurrency is slower than doing the work one at a time**.
`ecosystem.config.js` pins `instances: 1` in `fork` mode because caches, SSE fan-out and rate-limit
buckets are process-local; `docs/architecture-backlog.md` (D3) records the same constraint.

**Impact.** Throughput on the ledger path is bounded by cache refresh, not by PostgreSQL, and the
system cannot be scaled horizontally without redesign. Acceptable at 30 users; a hard ceiling at 100+.

**Remediation (P1).**
- Replace whole-cache refresh with per-entity invalidation (table → cache-key mapping) or versioned
  read-through keys; coalesce refreshes with single-flight so ten writes cause one reload, not ten.
- Publish change notifications **after commit** rather than re-reading caches synchronously.
- Once caches are shared (Redis or `pg_notify` + local invalidation), raise `instances` behind a
  load balancer; move rate-limit buckets and SSE fan-out to the shared store first.

#### H5 — Internal error detail is exposed to API callers
**Evidence.** 71 matches for `message: \`Database error: ${err.message}\`` / `message: err.message` /
`error: err.message` across `server/src/controllers` and `server/src/services` — for example
`server/src/controllers/admin.controller.ts:198,260,283,302,338`. These bypass the central error
handler and return PostgreSQL text (table and constraint names, sometimes values) to the client.
Separately, the **unauthenticated** `GET /api/db/status` returns
`{"isConnected":true,"host":"localhost","port":5432,"database":"inventory_db","user":"inventory_user","tableCount":179,...}`
and, when the probe fails, the raw driver message in `errorDetails`
(`server/src/controllers/misc.controller.ts:54-82`).

**Impact.** Reconnaissance for targeted injection/credential attacks, and disclosure of schema
internals to any client on the network; during an outage the public endpoint can echo driver-level
connection errors.

**Remediation (P0/P1).**
- Route every failure through the existing `ApiError` / central handler; log the detail with a
  correlation id and return `{ message, correlationId }` only.
- Reduce the public `/api/db/status` to `{ isConnected }`; move host/port/user/error detail behind a
  Super-Admin check (the setup banner already needs only the boolean).
- Add a CI guard (`check:no-error-detail-leak`) alongside `check:no-inline-sql`.

#### H6 — 121 foreign-key columns have no supporting index
**Evidence.** Live catalogue query (§10): 121 FK leading columns have no index whose first key
column matches. High-traffic examples: `purchase_orders.supplier_id`, `sales_invoices.fiscal_year_id`,
`gl_subledger_entries.journal_line_id`, `gl_subledger_entries.branch_id`,
`customer_payments.original_payment_id`, `fixed_assets.product_id`, `warranty_coverages.product_id`.
(The prior audit recorded 19; the schema has roughly doubled since.)

**Impact.** Parent deletes/updates (`ON DELETE SET NULL/CASCADE`) scan the child table under a lock,
and joins on these columns cannot use index nested loops. This worsens as the ledger and stock
history grow, and it interacts directly with H1/H4.

**Remediation (P1).** Migration `0030_fk_indexes` covering the hot columns above plus
`stock_operations.product_id`, `serial_log.product_id`, `shipments.destination_branch_id`,
`fiscal_year_balances.branch_id/account_id`; then add a CI guard comparing FK columns against
`pg_index` so the gap cannot reappear. Verify with `EXPLAIN (ANALYZE)` on the affected list pages.

## 5. Audited and Found Sound

These are positive findings with the evidence that supports them — they should be preserved, and
several of them are the reason this system's risk is Medium-High rather than Critical.

**Authentication primitives.** `scrypt` (16-byte salt, 64-byte key) with `timingSafeEqual`
comparison; HMAC-SHA256 tokens with 8-hour TTL; a `ver` session fingerprint (password, email, role,
branch scope, switch state, status) re-checked on **every** request, including the SSE stream; the
production boot refuses to start without a real `AUTH_TOKEN_SECRET`. (`server/src/middleware/auth.ts`,
`server/src/middleware/sseAuth.ts`)

**Authorization.** A 68-operation permission matrix, per-user overrides and permission-set grants,
enforced server-side together with branch scope, fiscal-year write access and approval workflows;
protected by dedicated authorization tests and `docs/authorization-audit-2026-10-28.md`. Role
assignment is itself restricted (only Super Admin / Sub Super Admin may assign anything beyond HR
Self Service). No privilege-escalation path was found.

**Ledger integrity.** `gl_journals`, `gl_journal_lines` and `gl_subledger_entries` carry
`BEFORE UPDATE/DELETE` append-only triggers (6 triggers verified live) plus registry-sync triggers;
`gl_journals` is partitioned monthly (29 partitions). Balanced-journal rules, document-number
allocation and stock movements are covered by concurrency tests.

**Schema governance.** 29 numbered migrations with immutable checksums (a modified migration is
rejected at boot); `verify_fresh_install.mjs` proves a fresh install produces a schema identical to
`schema.sql` + migration replay. This is a rare and valuable property.

**SQL hygiene and layering.** `check:no-inline-sql` passes over 49 controllers — SQL lives only in
repositories; `check:no-raw-dialogs` passes over 289 client files; `tsc --noEmit` is clean.

**Transport and input hardening.** `helmet` with a real CSP in production and test (dev disables it
because Vite needs inline scripts, documented at `server/src/app.ts:236-249`); body limit from
`JSON_BODY_LIMIT` with validation instead of NaN; compression threshold above 1 KiB with SSE
excluded; per-IP SSE connection cap; login throttling per IP and per account; generic
forgot-password response (no account enumeration).

**XSS posture.** No `dangerouslySetInnerHTML` or `innerHTML` assignment anywhere in `client/src`;
`script-src 'self'` plus the absence of HTML sinks means the localStorage token is not reachable by
stored XSS in practice (still see M3).

**Test and budget gates.** 2,411 tests across 290 files, including concurrency, drift, authorization
and docs-count guards; bundle budget (22.1/22.25 kB entry, 321.9/322 kB startup) and boot budget
(993/444 ms against 12 s) both enforced.

**Demo-data isolation.** Seeded rows are flagged (`is_demo`) with a clear-demo path, so demonstration
data cannot silently blend into go-live figures.

## 8. Go / No-Go Position

**Conditional Go.** The application is functionally complete and structurally sound enough to run
the business; it is not yet safe to *depend* on. The blocking set is small and specific: **backups
(C1), login-path scaling (H1), credential policy (H2), transport/at-rest encryption (H3)** and the
public diagnostic disclosure in **H5**. Once Phase 0 is closed and verified with the commands in
§10, the residual risk is Medium and the recommended position is **Go for a controlled rollout** with
the Phase 1 items tracked as conditions.

**What would move the rating to Low:** Phase 0 + Phase 1 complete, a load test at the real expected
concurrency on production hardware, a signed requirements baseline, and a successful restore drill
observed by operations.

## 9. Audit Limitations

- **No requirements document was supplied or found**, so "alignment with business requirements" is
  measured against the README's feature claims and the initiative notes; M6 records this gap rather
  than asserting coverage.
- **No production data was available.** Data-integrity findings concern schema, constraints,
  reference data and ledger mechanics; the accuracy of a real migrated dataset could not be assessed
  because no migration has been performed (M7).
- **Measurements were taken on a Windows development workstation** through loopback HTTP with the
  `tsx watch` dev process and a demo-seeded database. Latency figures are optimistic for production;
  they do not include TLS, a reverse proxy, or production hardware. The single-process ceiling
  (H1/H4) is a design property and transfers regardless.
- **No dynamic security testing or penetration test** was performed; findings are from code review,
  live API probing and configuration inspection. No exploitation was attempted.
- **CI on GitHub Actions could not be observed** (`gh` is unavailable in this environment); the CI
  jobs were replicated locally instead (`tsc`, guards, `npm audit --omit=dev` with 0 vulnerabilities,
  fresh-install parity, build, bundle and boot budgets — all green).
- The 2 failing tests noted during the last full suite run were a warranty-SLA clock flake at the
  midnight boundary, fixed in `b5f88d3` and re-verified green; no open test failure remains.
