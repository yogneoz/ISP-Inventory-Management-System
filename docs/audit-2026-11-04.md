# Full-project audit — 2026-11-04

_Read-only audit of the whole tree at commit `2e76bcf` plus the uncommitted
master-data work, which was committed as `5763759` at the end of the audit. Every
number below was produced by a command run against this machine's PostgreSQL,
not quoted from earlier documents._

Scope: project-wide. Build and test gates, schema and data integrity, HTTP/auth
surface, client resilience, dependency health, documentation truth, repository
hygiene. Findings are ordered by what would hurt first, and each one carries the
evidence that produced it.

## Verdict

The correctness posture is strong: strict TypeScript, controllers provably free
of SQL, every route authenticated by default behind a six-entry allowlist,
branch scope enforced twice, balanced-journal and atomic document-number
guarantees, and 1,913 tests green against real PostgreSQL.

Two CI gates fail on this tree (bundle budget, boot timing), and one design gap
matters beyond the build: sessions cannot be revoked. Those are the first three
items below.

## A. Blocking gates

### A1 — Startup bundle budget exceeded

`npm run check:bundle-budget` exits 1: the entry chunk is **19.3 kB gz** against
an 18 kB budget (the script's own comment records 17.1 kB on 2026-10-30), and the
startup total is **316.3 kB of 320 kB** — under 1% headroom.

Cause is legitimate growth, not a regression: the master-data work added three
finance screens, one sales screen and a new `services/api` domain, and the
`api` barrel is eagerly imported by the app root. The screens are lazy; the
barrel and its types are not.

### A2 — Boot-timing gate: the saved tab is not restored

`npm run check:boot-timing` exits 1 on both reloads:

```
✖ the settled screen was not "Create Sales Invoice" (got: ... Dashboard ...)
✖ active tab was "dashboard" instead of "create-sale"
```

The check seeds `inventory_active_tab` and pins the server-held `activeTab`
preference before navigating. `resolveInitialTab()` prefers that saved tab and
`isTabAccessible('create-sale')` is true for the demo Super Admin, so the lost
tab is a real restore-path failure, not a guard refusal. Either the pinned
preference does not reach the client's first hydration or the localStorage seed
loses its race with the first render; isolating it needs a browser trace.

## B. Security

### B1 — Sessions cannot be revoked

`verifyAuthToken` checks only signature and `exp`; nothing re-reads the user row
and there is no logout endpoint. Tokens are HMAC-signed, 8-hour TTL, and embed
`role`, `branchId` and `allowedBranchIds`. Therefore deactivating an employee,
demoting a role or resetting a compromised password leaves every issued token
fully valid until it expires. The permission matrix is read live; the role in the
token is not.

### B2 — Password reset discloses account existence

`POST /api/auth/forgot-password` answers **404** for an unknown email and 200 —
with the user's name and the Super Admin's email address — for a known one. That
is unauthenticated account enumeration plus internal address disclosure. The
route is rate limited, which caps the rate but not the leak.

## C. Client resilience

### C1 — No error boundary

There is no `ErrorBoundary`, `componentDidCatch` or `unhandledrejection` handler
anywhere in `client/src`. React 19 unmounts the root on an uncaught render
error, so one bad row in any of 82 screens blanks the application with no
recovery. The 8-second splash valve in `main.tsx` covers boot only.

### C2 — No request timeout or cancellation

Nothing under `client/src` uses `AbortController`. A stalled server leaves a
spinner forever, and the GET dedup map keeps the identical in-flight promise, so
every duplicate request joins the stuck call.

### C3 — A 204 response breaks the JSON client

`fetchJson` always awaits `res.json()`, while
`POST /api/customer-devices/exchange/refusal` answers `204 No Content`. Every
call therefore rejects with a `SyntaxError`; both call sites swallow it, so the
audit row is written but the promise is a permanent false failure. Any future
non-silent 204 would toast an error over a success.

## D. Server behaviour

### D1 — A cancelled statement marks the database offline

`pgPool.query` treats every SQLSTATE beginning `57` — including
`57014 query_canceled` and `statement_timeout` — as a disconnect, and any error
message containing `timeout`. One cancelled query flips the global connected
flag, so subsequent requests answer 503 until `requirePostgres` re-probes.

### D2 — Every mutation reloads the whole operational cache before replying

`cacheRefreshHook` re-runs all `CACHE_LOADS` through one serialized chain on any
successful non-GET. This is what keeps the mirrors honest, but write latency is a
function of catalog and document-table size, and all writes queue behind a single
chain. This is the documented single-instance consequence, and the first thing
that will hurt at volume.

### D3 — Nineteen FK columns have no supporting index

Highest-traffic: `sales_invoices.fiscal_year_id`, `purchase_orders.supplier_id`,
`stock_operations.product_id`, `serial_log.product_id`,
`gl_journals.fiscal_year_id`, `gl_subledger_entries.journal_line_id`.

Per the repo's own B1 doctrine (measure before indexing), only the columns that
a scoped read actually filters on were added; the rest stay recorded here rather
than guessed at.

### D4 — Master-code create is check-then-insert

Concurrent creates of the same area/agent/cost-centre/narration/bill-term code
surface as 500 (unique violation) instead of 409.

### D5 — `Boolean(body.active)` accepts `"false"` as true

All four master parsers coerce `active` with `Boolean(...)`, so a string
`"false"` enables the record. The client sends booleans, so it is latent.

### D6 — Demo-clear cannot reach five new master tables

`areas`, `sales_agents`, `cost_centers`, `narration_templates` and `bill_terms`
each carry `is_demo`, but none is in `DEMO_DATA_TABLES`, so "Clear Demo Data"
leaves them behind while their parent rows are removed.

## E. Data and documentation truth

### E1 — Fiscal-year 2085-86 has an impossible BS label

`fiscal_years.end_date_bs` for `2085-86` is `2085-12-31 BS`. BS 2085's Chaitra
has 30 days, so that day does not exist, and the AD sibling (2029-07-15) lies
past the end of the patro data, so the correct label (2086-03-30 BS) cannot be
derived. The project's own `audit:bs-dates` flags it as an error and correctly
refuses to guess — but the wrong label is what the fiscal-year screens display.

### E2 — README table counts are stale

README claims **38 tables** twice and **54 relational tables** once; the schema
and the parity test both say **57**. The docs-count gate checks test counts only,
so table counts drifted unnoticed.

## What was checked and found sound

- **Schema:** 57 tables, all with a primary key and at least one index; 136
  foreign keys with explicit `ON DELETE` behaviour (76 `SET NULL`, 37 `CASCADE`,
  23 `RESTRICT`); idempotent re-apply.
- **SQL injection:** no interpolated user input reaches SQL text. Page sizes and
  limits are clamped numerically at the controller (`Math.min/max`), ORDER BY
  fragments are constants, and identifiers come from fixed registries
  (`DEMO_DATA_TABLES`, `FISCAL_YEAR_LINK_TARGETS`, the `*_bs` column sweep).
- **Auth primitives:** scrypt with per-row salt and `timingSafeEqual`; HMAC token
  signatures compared in constant time; login and forgot-password rate limited
  per IP and per account.
- **Authorization:** every route sits behind `authenticateUser` plus an explicit
  six-path public allowlist; `requirePermission`/role gates on 165 routes and the
  app-level operational prefix rules cover the rest; branch scope enforced by the
  middleware registry and re-applied in SQL. The Step 5 area/agent masters were
  checked specifically: the branch-scope registry entry refuses a branch account
  read or write of another branch's (or a global) area before the controller runs.
- **Accounting integrity:** journals are refused unless balanced with exactly one
  side per line; document numbers are claimed atomically; schema parity and drift
  guards hold.
- **Client hygiene:** no `dangerouslySetInnerHTML`, no native
  `alert/confirm/prompt`, zero TODO/FIXME markers, all 82 screens pinned by the
  surface-coverage test.
- **Dependencies:** `npm audit` clean for production and dev trees.
